## 종합 판정

핵심 알고리즘(FNV-1a 해시 → 인덱스 → 렌더)은 **결정론적 추첨이라는 컨셉을 최소 코드로 정확히 구현**했고, 바닐라 단일 파일 앱으로서 스타일 일관성·접근성 기본기·XSS 안전 렌더링이 모범적이다. 4개 관점이 공통으로 칭찬한 부분이다.

부채는 **두 갈래**로 수렴한다:

1. **URL 라우팅 3중화(query/hash/path)** — 4개 관점이 *모두* 독립적으로 지적한 단일 최대 항목. 앱이 실제로 생성하는 URL은 query뿐인데 hash/path 파싱·역작성 로직이 약 70줄의 복잡도와 중복, 라우팅 비대칭(동등 입력이 다른 결과로 갈라짐)을 만든다.
2. **날짜/타임존 결정론 누수** — 핵심 컨셉("같은 URL ⇒ 같은 당첨자")이 *날짜를 생략한 공유 URL*에서 깨진다. 보는 사람의 로컬 날짜가 숨은 입력이 되어, 시점·타임존이 다르면 다른 당첨자가 나온다.

이 둘은 서로 얽혀 있다 — 라우팅을 query 단일로 정리하면서 공유 URL에 날짜를 강제 포함하면 두 부채가 동시에 줄어든다. 나머지는 중복 제거·의도 주석·네이티브 위임 수준의 경미~스타일 항목이다.

**한 줄 요약**: 컨셉과 알고리즘은 단단함. *URL 라우팅의 과설계*와 *날짜 없는 공유 URL의 재현성 누수*가 우선 해결 대상.

## 합의된 주요 발견 (상세)

### C1. URL 라우팅 3중화 — 4개 관점 전원 지적
- **위치**: `splitRoute` (L850–883), `getPathRouteSegments` (L885–896), `reflectMissingDateInUrl` (L913–939)
- **핵심**: 입력을 query(`?names=a,b,c`) / hash(`#/a,b,c/date`) / path(`/random-picker/a,b,c/date`) 세 경로에서 파싱하고, date 역작성도 경로별로 다르게 한다. 그러나 **앱이 생성하는 URL은 `buildExampleUrls`·`buildNamesUrl` 모두 query 형식뿐** — hash/path는 앱이 절대 만들지 않는 형식을 위한 speculative generality(Karpathy #2). 게다가 동등 입력이 경로별로 다른 당첨자로 갈라지는 케이스가 존재(핵심 관점 C/#3·#4).
- **확신도** 높음 · **심각도** 주요
- **제안**: query 단일 라우팅으로 축소하면 약 70줄 → ~15줄. hash가 정말 필요하면 *한 형식만* 택일. 이건 기능 축소 결정이므로 [ADR](../decisions/)로 남길 것.

### C2. `reflectMissingDateInUrl`이 라우팅 소스를 재추론
- **위치**: L913–939
- **핵심**: `splitRoute`가 이미 `source: "query"|"hash"|"path"`를 반환하는데, 이 함수는 그 정보를 받지 않고 `params.has("names")`·hash 재파싱으로 *독립적으로 다시 판별*한다. 두 판별 규칙이 미래에 어긋날 수 있고(단일 진실 원천 위반), date를 엉뚱한 위치에 pin할 여지(핵심 #8).
- **확신도** 높음 · **심각도** 주요
- **제안**: `source`를 인자로 전달해 추론 대신 분기. 함수 상단에 "date 누락 URL을 오늘 날짜로 고정해 공유 안정화" 의도 주석.

### C3. app-segment 탐색 중복 + 배포 경로 하드코딩
- **위치**: `getPathRouteSegments` (L885–896), `getBaseUrl` (L968–976)
- **핵심**: 두 함수가 `split("/").filter(Boolean)` 후 `"random-picker"`/`"random-picker.html"`를 `findIndex`로 찾는 동일 패턴을 복제. 폴더명이 바뀌면 두 곳을 함께 고쳐야 하고(Surgical change 저해), 배포 경로라는 외부 사실이 코드에 묻힌 가정으로 박혀 있다.
- **확신도** 높음 · **심각도** 주요(설계의도)/경미(간결성)
- **제안**: `const APP_SEGMENT = "random-picker"` 상수 + 탐색 헬퍼 1개로 추출, "배포 경로에 결합됨" 주석. (C1로 path 라우팅을 없애면 `getPathRouteSegments`가 통째로 사라져 동시 해소.)

### C4. 이름 정규화/인코딩 중복
- **위치**: `parseInput` L901–904 vs `normalizeNamesInput` L1036–1041 (split 체인 중복); 인코딩 `names.map(encodeURIComponent).join(",")`이 L918·959·1049 3곳(클린 #3).
- **확신도** 높음 · **심각도** 경미
- **제안**: `normalizeNamesInput(namesPart)` 재사용 + `encodeNamesPart(names)` 헬퍼로 통합. *이미 2회 이상 사용처가 있는 진짜 중복*이라 추출이 정당(1회용 추출 지양 원칙과 충돌하지 않음).

### C5. `<details>` 네이티브 토글 수동 재구현
- **위치**: L1154–1157 (+ `els.usageSummary` L836)
- **핵심**: `<summary>` 클릭은 브라우저가 `<details open>`을 공짜로 토글하는데, `preventDefault()`로 막고 `els.usageCard.open = !els.usageCard.open`로 똑같이 재구현. 핸들러를 지워도 동일 동작(CSS `[open]` 셀렉터도 유지). 리스너가 실제 `<summary>`가 아니라 자식 `.usage-title`에 걸려 네이밍·의도 불일치(클린 #7).
- **확신도** 높음 · **심각도** 경미
- **제안**: 핸들러와 `els.usageSummary`를 삭제, 네이티브 토글에 위임.

### C6. winner 텍스트를 상태 소스로 역참조
- **위치**: 클릭 핸들러 L1104 `els.winner.textContent.trim()`, `"-"` 가드 L1106
- **핵심**: `render()`가 이미 아는 `winner` 값을 보관하지 않고 DOM 텍스트를 다시 읽음(SSOT 역방향 의존). 이름이 실제로 `-`인 후보(`?names=-,b`)가 당첨되면 복사가 막히는 숨은 엣지(센티넬과 유효값 충돌).
- **확신도** 중간 · **심각도** 경미
- **제안**: 모듈 스코프 `let currentWinner`를 `render`에서 세팅, 핸들러는 그 변수 + `els.winner.disabled`로 가드.

### C7. `resizeCanvas` 2벌 중복
- **위치**: `launchBackground` L1170–1179 vs `launchConfetti` L1259–1268
- **확신도** 높음 · **심각도** 스타일
- **제안**: `setupHiDpiCanvas(canvas, context)` 헬퍼로 추출(선택적 — 각 함수가 독립 클로저라 추출 이득이 크지 않은 경계선).

### C8. 매직 넘버 / 결정론 시드의 "왜" 부재
- **위치**: FNV 상수 `2166136261`/`16777619` (L942·945), 토스트 1200/1400 (L1091·1100), star 90 (L1162), pieces 150 (L1241), duration 1900 + 350 (L1253·1304)
- **핵심**: 이 앱의 *존재 이유*인 결정론 해시에 "왜 랜덤이 아니라 해시인가" 주석이 없다 → 다음 사람이 "단순화"하다 결정론을 깰 위험(설계의도 #1, 주요). 타이밍/카운트 상수는 튜닝 포인트라 명명 가치 높음(클린 #8).
- **확신도** 높음 · **심각도** 주요(시드 의도)~스타일(상수)
- **제안**: `pickWinner` 위 1–2줄 의도 주석, FNV 상수에 `// FNV-1a offset basis / prime`, 타이밍 값 상수화.

### C9. confetti가 hashchange 재추첨에 안 터짐
- **위치**: 부트스트랩 L1308–1313, hashchange L1307은 `render` 반환값 폐기
- **핵심**: 축하 피드백이 최초 1회만. hash를 바꿔 새 당첨자가 나와도 confetti 없음 — 의도인지 누락인지 코드로 판단 불가(검증 가능 기준 부재, Karpathy #4).
- **확신도** 중간 · **심각도** 경미
- **제안**: "첫 로드만 축하"가 의도면 주석, "매 픽 축하"면 hashchange 경로에도 연결(같은 당첨자 재렌더 시 중복 방지).

### C10. `%2C→,` 치환 의도 불명
- **위치**: `reflectMissingDateInUrl` L923 `params.toString().replace(/%2C/g, ",")`
- **핵심**: 가독성 위해 인코딩된 콤마를 되돌리지만 주석 없음. `buildExampleUrls`/`buildNamesUrl`는 애초에 콤마를 인코딩 안 하는데(L959·1049) 여기선 인코딩 후 복원하는 비대칭. 전역 치환이라 다른 param의 `%2C`까지 건드릴 잠재 취약(현 date 포맷에선 무해).
- **확신도** 중간 · **심각도** 경미/스타일
- **제안**: 주석 추가 또는 공통 인코딩 헬퍼로 통일.

## 단독이지만 중요한 발견

### S1. 날짜 미지정 공유 URL의 타임존/날짜 결정론 누수 ★ 최우선
- **위치**: `todayInLocalTime` (L842), `parseInput` (L898–911), `render`(당첨자 계산 L1011 → date pin L1009 순서), `reflectMissingDateInUrl` (L913–939)
- **핵심**: `?names=a,b,c`(날짜 없음)를 열면 *당첨자 계산이 보는 사람의 로컬 날짜로* 끝난다. `reflectMissingDateInUrl`이 주소창 URL은 갱신하지만, (a) 이미 복사해둔 원본 링크, (b) OG/공유 미리보기, (c) date 없이 재공유되는 흐름을 못 막는다. 예: KST 6/11 16:00에 연 사람과 PST 6/10 23:00에 연 사람은 각각 `2026-06-11`·`2026-06-10` 시드 → **다른 당첨자**. "같은 URL ⇒ 같은 당첨자"라는 핵심 약속이 깨진다.
- **확신도** 높음 · **심각도** 주요(컨셉 핵심)
- **제안**: 공유용 URL(`buildExampleUrls`의 default 포함, `buildNamesUrl`)이 항상 `&date=`를 포함하도록 강제. 최소한 example "Today's default" 라벨을 "매일 바뀜"으로 정직하게 표기.
- **연관**: 핵심 #6(default 예시 URL이 날짜 미포함으로 결함을 권장 흐름에 노출), #7(starter-form 산출 URL도 날짜 없음).

### S2. `render()` 책임 과다 (SRP)
- **위치**: L1001–1034
- **핵심**: 파싱 + `history.replaceState` 부수효과 + 순수 계산 + 7개 이상 DOM 변형을 한 함수가 모두 수행 → 단위 검증 불가(전역 DOM/history 의존).
- **확신도** 높음 · **심각도** 주요
- **제안**: `computeResult()`(순수: 입력→{winner, names, date}) + `paintResult(result)`(DOM 전용)로 분리. Karpathy #4(검증 가능성)와 직결.

### S3. "새 탭에서 열기" UX 모델 미문서
- **위치**: starter-form submit L1118–1139 (`window.open(..., "_blank")` L1130)
- **핵심**: 앱이 `render()`(in-place)와 starter-form(new-tab) 두 UX 모델을 동시에 갖는데 "왜 새 탭인가"가 어디에도 없다. 같은 탭에서 여러 번 누르면 탭이 쌓임.
- **확신도** 높음 · **심각도** 주요
- **제안**: "각 뽑기를 독립 공유 URL로 분리" 같은 의도를 1줄 주석으로.

### 그 외 단독 경미/스타일 (간략)
- **핵심 #2** `% names.length` 모듈로 분포 편향 — 이론상 존재하나 `~10⁻⁹` 수준, **실사용 무시 가능**. 수정 불필요.
- **핵심 #5** 중복 이름(`a,a,b`)이 당첨 시 두 span 모두 `is-winner` — "어느 인스턴스가 뽑혔는지" 모호. 인덱스 기반 표시 권장.
- **핵심 #4** 이름에 `/` 포함 시 hash/path 모드에서 구분자와 충돌해 깨짐 — query만 안전. (C1 해소 시 동시 해결.)
- **핵심 #13** emoji/유니코드 결정론은 유지(UTF-16 코드유닛 기반, 로케일 무관). NFC/NFD 정규화 차이만 낮은 확률 엣지 — 실용상 불필요.
- **클린 #6** copy-button 핸들러 `target` null-safety 부재 — `if (!target) return;` 또는 `getElementById` 권장.
- **클린 #11** `showStarterMessage`가 성공/실패 메시지를 모두 `.error` 노드로 표시 — 네이밍·시맨틱 불일치.
- **설계의도 #7·#8** `aria-live` 중첩(winner-section ↔ winner-copy-status) 및 범위 모호 — 중첩 제거, `#copy-status` 초기 텍스트 비우기.
- **간결성 #7** `copyText`의 `execCommand` 폴백 — `file://`·iframe에선 발동 가능하므로 *완전한 사변 아님*. 배포 맥락에 따라 판단(아래 긴장 참조).
- **간결성 #8** `parseInput` 디폴트 파라미터(`= ""`)는 도달 불가 — `splitRoute`가 항상 문자열을 채움. 제거 가능.
- **간결성 #10** confetti 정리 2중화(progress 완료 + setTimeout 백스톱) — 의도는 정당(탭 백그라운드 시 rAF 정지 대비), `cleanup()`으로 묶기 권장.

## 관점 간 긴장 (트레이드오프)

상호 리뷰에서 관점이 *충돌*하는 지점은 단일 정답이 없으므로 결정자가 맥락으로 판단한다.

1. **단순성 ↔ 견고성/호환성**: 간결성 관점은 `execCommand` 폴백·copy-button null 가드·라우팅 3중화의 *제거*를 권하지만, 핵심/클린 관점은 호환성·견고성 가치를 본다. Karpathy #2는 "불가능한 시나리오엔 핸들링 불필요"라 하지만 `file://`·임베드 iframe은 *가능한* 시나리오다. → **로컬/임베드 사용을 지원하는가**로 판단. 지원 안 하면 폴백 제거(17줄 절감), 지원하면 유지(정당).
2. **중복 이름 = 가중치 ↔ 표시 모호**: 중복을 제거하지 않는 건 fair-pick 컨셉상 "가중치"로 정당화 가능하나, 시각 피드백이 어느 인스턴스가 뽑혔는지 못 보여준다. → 정책을 *명시*(라벨)하거나 인덱스 기반 표시로.
3. **라우팅 유연성 ↔ 단순성·일관성**: 4관점 모두 단순화를 시사하나, hash/path가 *의도된 기능*이라면 제거 대신 우선순위·제약을 문서화로 해소. → 기능 의도 확인 후 ADR.

## 잘 된 점 (교차검증된 긍정)

- **결정론 알고리즘** (`hashString` L941–950, `pickWinner` L952–956): FNV-1a + `Math.imul` + `>>> 0`로 크로스 브라우저 결정론 확보, 시드 `names.join(",")|date`가 순서·날짜를 모두 반영. 외부 의존성 0 — 레포 에토스에 완벽 부합. *(간결성·핵심·클린 공통 칭찬)*
- **XSS-safe 렌더링**: `replaceChildren` + `textContent`로 후보 리스트 구성(L1024–1031), innerHTML 문자열 조립 회피. *(간결성)*
- **접근성/모션 존중**: `prefers-reduced-motion` 분기(L1223·1234), `aria-label` 동적 갱신(L1019), 장식 캔버스 `aria-hidden`. *(설계의도·핵심·클린 공통 — 의도가 코드에 가장 잘 드러난 모범)*
- **`copyText` 폴백 + 의도 주석**(L1057–1083): "왜 폴백이 필요한가"가 주석으로 명시 — 침묵 삼킴이 아님. *(설계의도·핵심·클린)*
- **`opened.opener = null`**(L1133): reverse-tabnabbing 방어, 작지만 정확한 디테일. *(클린)*
- **스타일 일관성**: 더블쿼트, `const` 우선(`let`은 진짜 가변값에만), early-return 가드절, 얕은 중첩. *(클린·설계의도)*

## 부록 — 관점별 원본 리뷰 (사전 필터링 없음)

아래는 4개 관점 에이전트가 반환한 원본 발견 목록이다. 위 종합은 이들의 교차검증 결과다.

### 부록 A — 간결성 관점

**렌즈 판정**: 핵심 로직은 충분히 간결하나, URL 라우팅 3중화와 역방향 URL 재작성이 실제 필요보다 훨씬 많은 복잡도를 끌어들인다 — 이 파일의 단일 최대 간결성 부채.

1. **URL 라우팅 3중 전략** (`splitRoute` L850–883, `getPathRouteSegments` L885–896, `reflectMissingDateInUrl` L913–939) — 앱이 생성하는 URL은 query뿐이라 hash/path는 speculative generality. ~70줄→~15줄 축소 여지. 〔높음·주요〕
2. **`reflectMissingDateInUrl` 비용 대비 가치** (L913–939) — #1의 3중 분기를 떠안아 가장 복잡한 함수. query-only 전제면 3~4줄로 축소. 〔높음·경미〕
3. **`getBaseUrl`/`getPathRouteSegments` 중복** (L885–896, L968–976) — app-index 탐색 패턴 복제. 〔높음·경미〕
4. **`normalizeNamesInput` vs `parseInput` 파싱 중복** (L901–904, L1036–1041) — split 체인 중복, 이미 2회 사용처라 추출 정당. 〔높음·스타일〕
5. **`els`의 미사용/저활용 참조** (L824–839) — `usageSummary`는 #6 해소 시 제거 가능. 나머지 캐싱은 유지 무방. 〔중간·스타일〕
6. **`<details>` toggle 수동 재구현** (L1154–1157) — 네이티브 동작을 끄고 동일 동작 재구현, accidental complexity. 〔높음·경미〕
7. **`copyText` execCommand 폴백** (L1057–1083) — HTTPS 배포면 dead path 근접하나 file://·iframe에선 발동 가능, 완전한 사변은 아님(17줄). 〔중간·스타일〕
8. **`parseInput` 도달 불가 디폴트 파라미터** (L899) — `splitRoute`가 항상 문자열 반환하므로 `= ""`는 미발동. 〔높음·스타일〕
9. **`resizeCanvas` 2벌 중복** (L1170–1179, L1259–1268) — 독립 클로저라 추출 이득 경계선. 〔중간·스타일〕
10. **confetti 정리 2중화** (L1288–1295, L1300–1304) — 백스톱 의도는 정당, `cleanup()`으로 묶기. 〔중간·스타일〕

*긍정*: 핵심 알고리즘 간결·무군더더기, `replaceChildren`+`textContent` XSS-safe, 상태 토글 집약(추적 가능), CSS 중복 거의 없음.

### 부록 B — 설계 의도 관점

**렌즈 판정**: 결정론 picker 의도는 코드로 잘 드러나나, 세 라우팅의 우선순위·암묵 가정과 "새 탭 열기" UX 모델이 미명시 — 가장 복잡한 서브시스템이 자기 설명을 못 함(Karpathy #1).

1. **결정론 시드의 "왜" 부재** (`hashString` L941–950, `pickWinner` L952–956) — FNV-1a·`Math.imul`·`>>>0`·시드 포맷·매직 넘버에 주석 0. 다음 사람이 "단순화"로 결정론을 깰 위험. 〔높음·주요〕
2. **세 라우팅 우선순위 무문서** (`splitRoute` L850–883) — query→hash→path fallthrough가 코드 흐름으로만. 빈 `?names=`가 hash/path를 가리는 미묘 동작. 〔높음·주요〕
3. **`reflectMissingDateInUrl`이 라우팅 재추론** (L913–939) — `source`를 안 받고 독립 재판별, 의도 주석 없음. 〔중간·주요〕
4. **`"random-picker"` 리터럴 결합** (L885–896, L968–976) — 배포 경로 가정이 두 곳에 복붙, 리네임 시 조용히 깨짐. 〔높음·주요〕
5. **"새 탭 열기" UX 모델 미선언** (L1118–1139, 에러메시지 L1005) — in-place와 new-tab 두 모델 공존, 정본 불명. 〔높음·주요〕
6. **`%2C→,` 미용적 디코딩 의도 없음** (L923) — 표준 인코딩을 일부러 깨는데 이유 부재, 다른 함수와 비대칭. 〔중간·경미〕
7. **접근성 의도 일부 불일치** (L763·777·817) — `aria-live` 중첩, `#copy-status` 초기 텍스트 상존. reduced-motion은 모범. 〔중간·경미〕
8. **`aria-live` 범위 모호** (L763·1017) — winner만 공지 의도면 영역을 좁혀야. 〔낮음·경미〕
9. **`render()` 반환값 계약 암묵** (L1006·1033·1307–1313) — confetti 트리거로만 쓰이고 hashchange는 폐기. 〔중간·경미〕
10. **winner 텍스트를 신뢰 출처로 재사용** (L1103–1116) — DOM이 SSOT, `"-"` 센티넬과 충돌(`?names=-,b`). 〔중간·경미〕
11. **매직 넘버 의도 부재** (L1253·1304·1162·1241·1091·1100) — 특히 `duration+350`의 `350`. 〔낮음·스타일〕

*긍정*: `dateWasMissing` 플래그가 의도 명확 전달, `copyText` 폴백 주석, reduced-motion 처리가 의도가 가장 잘 드러난 부분.

### 부록 C — 핵심 피처/컨셉 관점

**렌즈 판정**: FNV-1a 결정론 추첨 컨셉은 대체로 견고하나, (1) 날짜 미지정 시 타임존/날짜 경계 결함, (2) 라우팅 3종에서 동등 입력이 갈라지는 경로로 "같은 URL ⇒ 같은 당첨자, 공유·재현 가능" 약속이 특정 시나리오에서 깨진다.

1. **날짜 미지정 공유 URL이 사람·시점마다 다른 당첨자** (L842·898–911·1001–1011·913–939) — 당첨자 계산이 date pin 전에 로컬 날짜로 끝남. 복사된 원본·OG·재공유를 못 막음. 〔높음·주요〕
2. **`% names.length` 모듈로 편향** (L954) — `~10⁻⁹` 수준, 실사용 무시 가능. 〔높음(존재)/영향 무시·경미〕
3. **빈 `names=` 시 path/hash fallback 없음, 우선순위 비대칭** (L850–883) — "query에 빈 names" vs "names 없음"이 비대칭. 〔높음·경미〕
4. **path/hash에서 이름에 `/` 포함 불가** (L885–896·876–882) — `a/b`가 names/date로 오해석, query만 안전. 〔높음·경미〕
5. **중복 이름 표시 비일관** (L901–904·952–956·1024–1031) — `a,a,b`에서 두 `a` span 모두 `is-winner`. 〔높음·경미〕
6. **example "Today's default"가 날짜 미포함** (L958–966·978–982) — 재현 불가 URL을 1급 공유 예시로 제시. 〔높음·주요〕
7. **starter-form이 날짜 없는 URL을 새 탭으로** (L1048–1051·1118–1139) — 진입 피처가 #1 결함 내포. 〔중간·경미〕
8. **hash pin 분기가 잘못된 키로 history 갱신 가능** (L929–934) — `source` 미사용 재추론으로 무관한 `#section` 파괴 여지. 〔중간·경미〕
9. **`%2C→,` 전역 치환 취약** (L923) — 현 date 포맷엔 무해하나 round-trip 안정성 약화. 〔중간·스타일〕
10. **단일 이름 시 항상 자기 당첨 + confetti** (L1004·954) — 정상 동작, 과한 축하. 〔높음·스타일〕
11. **hashchange만 듣고 popstate/query 미반응** (L1307) — 현 구현상 실버그 아님(풀 로드 전제). 〔중간·경미〕
12. **confetti가 첫 로드만, hashchange 재추첨 누락** (L1308–1313) — 축하 피처 비일관. 〔높음·경미〕
13. **emoji/유니코드 결정론 유지, NFC 정규화만 엣지** (L941–950) — 컨셉 잘 지킴, NFC는 낮은 확률. 〔높음(결정론)/정규화 낮음·스타일〕

*긍정*: 시드 설계(순서·날짜 반영, 크로스 브라우저 결정론), 공유 URL 자기-치유, copy 폴백, reduced-motion 분리 — 컨셉을 잘 지키는 핵심들.

### 부록 D — 클린코드 관점

**렌즈 판정**: 바닐라 단일 파일로서 전반적으로 매우 깔끔(`els` 캐시, 순수 함수, 일관 스타일). 다만 `render()` 책임 과다, 라우팅/정규화 중복 3건, UI 텍스트를 상태로 읽는 스멜, 네이티브 동작 충돌 1건이 정리 대상.

1. **`render()` SRP 위반** (L1001–1034) — 파싱+URL변형+선정+7개 DOM 변형. `computeResult`+`paintResult` 분리 권장. 〔높음·주요〕
2. **이름 정규화 중복** (L901–904 vs L1036–1041) — 동일 파이프라인. 〔높음·주요〕
3. **이름 인코딩 3중 중복** (L918·959·1049) — `encodeNamesPart` 통합. 〔높음·경미〕
4. **app-segment 탐색 중복** (L885–896 vs L968–976) — `findAppIndex` 헬퍼. 〔높음·경미〕
5. **winner 값을 DOM 텍스트에서 역참조** (L1104) — SSOT 위반, `"-"` 매직 문자열 재검사. 〔중간·경미〕
6. **copy-button 핸들러 null-safety 부재** (L1143–1146) — `target` null이면 TypeError가 catch에 흡수(원인 은폐), 셀렉터 인젝션 표면. 〔중간·경미〕
7. **`usageSummary` preventDefault + 수동 토글** (L1154–1157) — 네이티브 시맨틱과 경쟁, 리스너가 `.usage-title`(자식)에 걸림. 〔중간·경미〕
8. **매직 넘버 산재** (L1091·1100·1162·1241·1253·1304) — 타이밍/카운트 상수화, FNV 상수 주석. 〔중간·스타일〕
9. **`resizeCanvas` 2벌 중복** (L1170–1179 vs L1259–1268) — 추출 트레이드오프 존재. 〔높음·스타일〕
10. **토스트 함수 2벌 중복** (`showCopyStatus` L1085–1092 vs `showWinnerCopyStatus` L1094–1101) — `makeToast(element, ms)` 팩토리. 〔높음·스타일〕
11. **`showStarterMessage`가 `.error` 노드 재사용** (L1043–1046, 호출 L1124·1134·1138) — 성공/실패 동일 노드, 네이밍 vs 시맨틱 불일치. 〔중간·경미〕
12. **`els` 네이밍 불일치** (L836 `usageSummary`가 실제론 `.usage-title`) — 캐시 키가 실제 DOM 오인. 〔높음·스타일〕

*긍정*: 순수 함수 분리, early-return 일관, `copyText` 폴백 주석(침묵 삼킴 아님), 접근성 기본기, `opened.opener=null` 탭나빙 방어, 스타일 일관성.
