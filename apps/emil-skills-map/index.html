Part 1 · 02 배경

왜 이런 차이가 생길까

"Almost every 'taste' decision has a logical reason if you look close enough."Emil Kowalski, 에세이 「Agents with Taste」

취향처럼 보이는 결정에도 대부분 이유가 있다는 뜻입니다. README는 "Agents don't have great taste"로 시작합니다. 에이전트는 동작하는 UI를 만들지만 ease-in과 ease-out 같은 작은 선택을 자주 틀리고, 이 레포는 그 이유를 규칙과 수치로 적어 에이전트가 따르게 합니다.

이 사람의 규칙을 믿을 만한 이유

주 9,300만그가 만든 Sonner(토스트)와 Vaul(드로어)의 npm 주간 다운로드 합계. 2026년 11월 10~16일 집계.
Vercel · Linear디자인 엔지니어로 디자인 시스템과 제품 화면을 만든 곳. 웹 애니메이션 강의 animations.dev도 운영합니다.
57.8k이 레포의 GitHub 스타. 2026년 3월 공개 후 약 8개월.

방금 본 More 메뉴를 새로 만든다면 /animate, 이미 만든 메뉴를 점검하려면 /review-animations. 나머지 스킬도 "지금 어떤 상황인가"로 고르게 되어 있습니다.

Part 1 · 03 지도

스킬 지도

기능을 새로 만들 때는 위쪽 흐름, 이미 있는 앱을 손볼 때는 아래쪽에서 고릅니다.

라우터 스킬 ask-emil이 20개 스킬을 묶어 둔 구조입니다. 스킬을 누르면 언제 쓰는지와 무엇을 돌려주는지가 나옵니다. 상황부터 찾고 싶다면 이럴 땐 이 스킬로 건너뛰세요.

예: 위의 팀 멤버 카드에 More 메뉴를 붙인다면

  1. 메뉴를 직접 짜기 전에 로 믿을 만한 라이브러리를 고릅니다.

  2. 가 애니메이션이 필요한지부터 묻고, 커브와 시간과 시작 위치를 고릅니다.

  3. 로 긴 이름, 1명, 0명 같은 최악의 데이터를 넣어 깨지는 곳을 찾습니다.

  4. 로 바뀐 코드의 모션을 엄격하게 검토받습니다.

  5. 같은 교정을 여러 번 했다면, 세션을 닫기 전에 로 규칙을 남깁니다.

Part 1 · 05 치트시트

치트시트에서 고른 규칙

스킬을 부르지 않아도 바로 쓸 수 있는 값들입니다.

레포에는 문제와 해결을 한 줄씩 짝지은 치트시트 두 개가 들어 있습니다. 앞의 두 개는 직접 눌러 볼 수 있습니다.

눌렀는데 반응이 없는 버튼

피드백 없음
:active → scale(0.97)

누르고 있는 동안의 차이를 보세요. 오른쪽은 160ms ease-out으로 살짝 줄어듭니다.

내 프로젝트에서 찾으려면 /find-animation-opportunities. :active 상태가 없는 요소를 찾아 이 값을 제안합니다.

상태가 바뀔 때 글자가 겹쳐 보이는 전환

opacity만 교차
+ filter: blur(2px)

눌러서 글자가 바뀌는 순간을 비교하세요. 오른쪽은 흐림이 두 상태를 하나로 이어 줍니다.

이 규칙은 /emil-design-eng에 있습니다. 전환들이 전반적으로 어색하다면 /improve-animations로 감사부터 받아 보세요.

UI 치트시트 (11개)

문제해결
오래된 타임스탬프가 "340 days ago"로 보임일주일이 지나면 절대 날짜로 바꾸기
숫자가 바뀔 때 흔들림font-variant-numeric: tabular-nums
큰 헤딩이 어색해 보임-0.02em처럼 자간을 좁게
본문이 읽기 불편함max-width: 65ch로 한 줄을 약 65자로
버튼이 반응하지 않는 느낌:active에 transform: scale(0.97)
아바타가 타원으로 찌그러짐아바타에 flex-shrink: 0
그라데이션 페이드에 경계가 보임ease 곡선을 따라 색 정지점을 더한 eased gradient
전환이 여전히 어색함전환하는 동안 filter: blur(2px)
드롭다운이 굼뜸300ms 미만의 ease-out, ease-in은 쓰지 않기
팝오버가 엉뚱한 곳에서 커짐transform-origin을 트리거 쪽에 (모달은 가운데 유지)
"1 members"로 표시됨Intl.PluralRules로 복수형 처리

성능 치트시트 (7개)

문제해결
애니메이션이 버벅임width·top 대신 transform·opacity
긴 리스트의 스크롤이 느림가상화: 보이는 항목만 렌더링
blur가 성능 문제를 일으킴애니메이션되는 blur()는 20px 미만으로
Motion의 x/y에서 프레임이 떨어짐motion 14.2 이상으로 올리거나 transform 문자열 사용
의도하지 않은 속성까지 애니메이션됨transition: all 대신 속성을 하나씩 지정
React가 매 프레임 리렌더링함state 대신 ref.current.style에 쓰기

Part 2

만드는 사람의 관점

스킬을 쓰는 것과 별개로, 스킬을 만드는 방식에서 가져갈 것 5가지.

여기부터는 내 스킬이나 CLAUDE.md를 쓸 때 참고할 점입니다. 오른쪽 "내 스킬에 적용"은 레포 원문이 아니라 이 글의 제안입니다.

  1. 01

    이유를 적고, 필요한 곳에는 수치를 적는다

    레포 근거

    "부드럽게" 대신 "ease-out, 드롭다운 150~250ms"처럼 씁니다. learn-taste는 다음 에이전트가 이유를 비슷한 상황으로 넓혀 적용하므로, 틀린 이유는 이유가 없는 것보다 나쁘다고 봅니다.

    내 스킬에 적용

    "적절히", "부드럽게" 같은 형용사를 찾아 값이나 범위로 바꾸고, 규칙마다 한 줄짜리 이유를 붙입니다.

  2. 02

    하지 않는 일을 적는다

    레포 근거

    improve-animations와 find-animation-opportunities는 코드를 고치지 않고, remove-animations는 빼기만 하고, review-animations는 모션 외 코드는 리뷰하지 않습니다. 경계가 분명해 고르기도 쉽습니다.

    내 스킬에 적용

    SKILL.md에 "하지 않는 일" 섹션을 두고, 이웃 스킬과 겹치는 지점에서 어느 쪽이 맡는지 적습니다.

  3. 03

    이유를 지어내지 않고, 추론한 이유는 확인받는다

    레포 근거

    learn-taste는 사용자가 말하거나 고치거나 확인한 것만 규칙으로 만듭니다. 추론한 이유에는 표시를 달아 확인받고, 승인한 것만 기록합니다.

    내 스킬에 적용

    규칙을 기록하는 스킬이라면 "확인됨"과 "추론"을 구분해 표시하고, 추론은 승인 뒤에만 저장하게 합니다.

  4. 04

    문장보다 체크

    레포 근거

    코드로 찾을 수 있는 위반은 lint 규칙, 토큰 제한, 테스트로 제안합니다. 긴 파일 속 문장은 컨텍스트가 차면 건너뛰어지지만, 체크는 매번 실행됩니다.

    내 스킬에 적용

    기계로 잡을 수 있는 규칙은 ESLint·stylelint 규칙이나 design token 제한으로 옮기고, 문서에는 잡을 수 없는 판단만 남깁니다.

  5. 05

    시점이 중요한 스킬은 직접 부르게 둔다해석

    레포 근거

    자동 선택을 끈 5개는 라우터, 프로토타입, 라이브러리 선택, 리뷰, 세션 회고입니다. 레포에 이유는 적혀 있지 않지만, 모두 사용자가 시작 시점을 정하는 편이 나은 일로 보입니다.

    내 스킬에 적용

    리뷰, 회고, 배포처럼 실행 시점이 결과를 좌우하는 스킬은 disable-model-invocation: true로 두고 사용자가 부르게 합니다.

오늘 바로 해 볼 것

같은 디자인 수정을 두 번 이상 했다면, 세션을 닫기 전에 /learn-taste

그 교정들을 이유가 붙은 규칙 후보로 정리해 주고, 승인한 것만 다음 에이전트가 읽을 곳에 남깁니다.

이 페이지의 모션은 레포 규칙(ease-out 커브, 300ms 미만, 모션 감소 설정 존중)을 따릅니다. 데모의 규칙 미적용 버전만 의도적으로 규칙을 어깁니다.
